# Initial request and decline notifications

Migration 000029 creates delivery rows transactionally for new pending requests and transitions to declined. It does not backfill existing requests: earlier send outcomes are unknown. Mentee and moderator initial notices remain eligible after transitions to contacted, working, done, declined or unavailable; a mentor notice is eligible only while pending, to avoid requesting action on a processed request. Decline messages are eligible only while declined. A delayed initial notice may arrive after the final-status notice. Completed-session and acceptance notifications use their existing separate paths.

Each recipient has a separate claim and sent marker. The worker retries failed deliveries and callbacks lost after commit through the `retry-request-deliveries` cron, at most 50 request groups per pass with a two-minute pass timeout and ten-minute retry deferral. Claims expire after three minutes; completion checks the claim token. A send has a one-minute context deadline. These bounds assume the email transport honors context cancellation. A provider may accept a message despite an error, timeout or a process dying before its sent marker is committed. A retry can then duplicate it; this is not exactly-once delivery. No historical rows are automatically replayed.

To run retries without any other cron job, deploy the worker with `WORKER_CRON_ENABLED=false` and `WORKER_REQUEST_EMAIL_RETRY_ENABLED=true` (default false). Pass the latter through the deployment environment and restart the worker; do not turn on the full cron schedule, which includes irreversible profile purging. Both retry jobs run every ten minutes. Acceptance retries select at most 100 records with a two-minute pass deadline and a one-minute send deadline; acceptance claims expire after 15 minutes. Same-job scheduled/manual/replica overlaps use a PostgreSQL advisory lease; individual claims coordinate callbacks and retries. Full cron already includes these jobs, so enabling both flags does not register duplicates. Shutdown stops the scheduler and waits up to 30 seconds before continuing; an interrupted claim is recovered after its lease expires. Sender and database must honor cancellation for deadlines to bound execution.

For a future rollout, coordinate the schema and worker cutover: old workers do not update these delivery rows, so running old workers against the new trigger can send a message and leave it pending for a new worker to send again. Pause request writes and stop old workers, apply the migration, start updated workers, then resume writes. Rolling back 000029 drops pending delivery state; drain or explicitly reconcile it first. This document is not an authorization to deploy.

## Safety and reconciliation

Both retry jobs, including manual cron triggers, skip before listing or claiming work unless `APP_ENV=production`, a nonblank `DEV_EMAIL_OVERRIDE` is configured, or **both** `WORKER_REQUEST_EMAIL_RETRY_ENABLED=true` and `WORKER_REQUEST_EMAIL_LIVE_RECIPIENTS=true` are set. The live-recipient flag defaults to false and is an explicit authorization to contact real people from non-production; use it only after verifying the database, queue, transport and intended recipients. It does not activate any scheduler on its own. When `WORKER_CRON_ENABLED=false`, the retry flag schedules only the two retry jobs; do not enable full cron for this purpose. A configured override still wins and reroutes all messages, even with the live flag; clear it only after deliberate operator review. In non-production the standard email sender reroutes all mail to that override; choose and independently verify an operator-controlled sandbox inbox and sandbox transport, and remember messages may contain personal information. The retry scheduler flag alone does not grant permission to contact arbitrary recipients. The gate covers retry jobs only, not direct event callbacks or other worker jobs. `APP_ENV=production` permits real recipients: never use it against copied production data or for a staging smoke test. A sandbox run marks deliveries sent in its database, so use an isolated copy, never production data/state.

Before cutover pause writes and old workers as above. Inventory requests created before migration, especially pending ones, and compare provider delivery records and application logs per recipient. Missing rows are **unknown**, not proof of non-delivery. Do not bulk insert or automatically replay historical records: reconcile each recipient and obtain operator approval for any manual resend, accounting for duplicate risk and current request status. New rows created while an old worker remains active must likewise be reconciled before enabling retries. Keep an audit of decisions; inaccessible provider records mean the outcome remains unknown.

Request retry `EmailFailures` counts failed request groups (a group may contain several recipients, or fail on a database/lookup error), not individual failed emails; `EmailsSent` is not populated for that job. Acceptance retry counts attempted failures and successful sends. Any failed group or acceptance send makes the overall cron run fail and returns a partial summary; subsequent groups are still attempted. Deferral applies even on failure.
