# Interface internationalization

## Scope and ownership

The application uses the **Next.js Pages Router**, with `ru` as the default language and `en` as the second language. Russian URLs retain existing paths; English URLs use `/en`. Browser language does not override the default. The locale in the URL is authoritative, including on SSR and reload. A language switch also records the non-sensitive `NEXT_LOCALE` preference cookie; opening an unprefixed URL still explicitly selects Russian.

Localization changes presentation, not product semantics. Do not change canonical tag strings, status codes, filter identifiers, analytics values, prices/currency, slugs, API contracts or database schema when translating labels. User profile content and requests are not machine-translated.

Public pages, forms, mentor workflows, and the shared administrator/moderator portal use the same translation infrastructure. Administrator navigation, login, moderation lists, mentor detail/actions, request management, and the analytics/vacancies/research section shells have domain dictionaries in `i18n/messages/admin*.ts`. The moderator view uses the same `/admin` routes with role restrictions; translated labels never replace role/status identifiers. BFF routes and Go backend behavior remain unchanged. New admin features should use the shared API below instead of introducing separate language state. Coordinate shared layout/provider/Next config edits across parallel work.

## Adding interface copy

Keep domain dictionaries in `web/src/i18n/messages/`. Use meaningful stable keys instead of English source sentences as keys:

```tsx
import { useTranslation } from '@/i18n'
import type { Messages } from '@/i18n/core'

const messages = {
  title: { en: 'Research', ru: 'Исследования' },
  results: {
    en: { one: '{count} result', other: '{count} results' },
    ru: { one: '{count} результат', few: '{count} результата', many: '{count} результатов', other: '{count} результата' },
  },
} satisfies Messages

export function ResearchTitle({ count }: { count: number }) {
  const { t } = useTranslation(messages)
  return <h1>{t('title')} · {t('results', { count })}</h1>
}
```

`useTranslation(messages)` returns `t`, `locale` (`ru` or `en`) and `intlLocale` (`ru-RU` or `en-US`). `createTranslator(locale, messages)` is the equivalent for non-React/server helpers. `formatNumber` and `formatDate` in `i18n/core` use Intl, including Russian plural rules. Keep rich markup in React rather than translated HTML strings; interpolation returns text and must not be passed to `dangerouslySetInnerHTML`.

A missing Russian entry falls back to its English entry. New production dictionaries should include both languages. The dictionary tests enforce matching interpolation parameters. A new language requires extending `Locale`, `locales`, `normalizeLocale`, `intlLocale`, Next's i18n configuration, switcher options and the domain dictionaries.

## Display-only taxonomy

Use `translateLabel(locale, rawValue)` from `@/i18n/labels` for stored tags, category/filter labels, experience and price labels. Keep option `value`, request payloads and analytics properties canonical. Unknown/custom labels are rendered unchanged. Ecological taxonomy and branding are a separate product change, not this translation layer.

## Routing and state

Use ordinary Next `Link`/router navigation to retain the active language. `LanguageSwitcher` changes only the locale, preserving dynamic route/query/hash and using shallow navigation so in-progress component/form state is not discarded. Do not key the page component by locale or add reload-based language switches. Hardcoded external links and third-party calendar widgets are outside Next's routing and are not translated automatically.

For server-generated links or metadata, `localizedPath(path, locale)` prefixes/removes `/en` without changing slugs, query parameters or fragments. Public pages publish locale-aware canonical/hreflang metadata and both URL languages in the sitemap. Keep private pages `noindex`.

## Testing

Wrap localized component tests in `<I18nProvider locale="ru">`. The real application always provides the route locale, defaulting to Russian. Isolated components without a provider retain English as an explicit compatibility fallback for the upstream test suite and embedding contexts; do not rely on this fallback in application code.

```sh
(cd web && npm test -- --runInBand src/i18n/__tests__)
(cd web && make pre-commit)
(cd web && make build)
```

Verify SSR language, RU↔EN navigation, reload, query/hash preservation, populated filters, entered form state, canonical payloads, destructive confirmations, private sessions, browser errors and mobile overflow against the running app. Build separately from the active dev server to avoid sharing `.next` output.

## Deliberate boundaries

Existing legal text is translated as upstream content, not adapted to a new operator, country or client. Existing operator names, contacts, dates and external destinations are not replaced. Mail templates and backend diagnostic error text are not localized by the frontend. Third-party calendars and anti-bot UI may use their own localization settings. Colors, ecological positioning, currencies and functionality are separate subsequent changes.
